# Plan: Chat/Servers Architecture Decision + Phased Roadmap

## Summary

Add a Discord-like chat area to plural-profiles: servers, channels, messages, threads, invite-based membership with blocking, and Tupperbox-style profile "proxying" (a short code in a message swaps the displayed avatar/name/pronouns for one of the author's profiles, linking to its public page). Servers/channels should be themeable using the existing theme system, and messages need the same hearts/spoilers formatting as descriptions.

The open question was structural: build this as a namespaced module inside the existing Rails app, or as a wholly separate Rails app talking to plural-profiles over an API? This matters because of two things already in play: the app is memory-constrained on Scalingo (currently moving from 1×M/512MB to 1×L/1GB after diagnosing swap pressure), and Scalingo is moving toward limiting swap, so future memory headroom is a real constraint, not a hypothetical. Chat adds two historically memory/connection-hungry ingredients — websockets and a fast-growing messages table — so the decision needs to hold up under that constraint, not just under "what's architecturally elegant."

This plan resolves the monolith-vs-separate-app question, sketches the domain/subdomain, realtime, and data-growth strategy, and lays out a build order. It intentionally does **not** spec exact schemas/columns for anything past Phase 1 — later phases get their own planning pass when the team is ready to build them.

### Key decisions from discussion

- **Realtime from day one** — true live updates via websockets, not polling
- **Path-based server/channel routing** under a single `chat.` subdomain, not per-server subdomains
- **Architecture + phased roadmap only** — later phases don't get exact schemas yet, those get their own planning pass

## Decision: build it inside this app, as a clearly isolated module — not a separate Rails app

**Recommendation: monolith**, structured as a `Chat::` namespace (models/controllers/views under `app/**/chat/`), with three specific isolation techniques that get most of what a separate app would buy, without the costs:

1. **Chat models stay in the primary database — no physical split on day one.** The original draft of this plan proposed a second Postgres database for chat models from Phase 0. On reflection that's premature: Rails' multi-database support doesn't do real SQL joins across two physical databases, and Postgres can't enforce foreign keys across them either. Since almost every chat query needs both chat data and identity data (messages need authors, memberships need users, proxied messages need profiles), splitting early means paying that cost on every query from day one, plus doubling test/CI database setup, for a scale problem that doesn't exist yet. Instead: chat models get a `ChatRecord < ApplicationRecord` abstract base class as a *seam* (not a split) — it points at the same connection as everything else to start, with plain `belongs_to :user`/`belongs_to :profile`, real FKs, real joins. If the messages table ever genuinely becomes a backup/vacuum/migration-time problem, repointing `ChatRecord` at a second database later is a much smaller job than designing around cross-database joins from the first migration. **Verified this pivot doesn't box anything in**: Scalingo explicitly supports and documents attaching multiple PostgreSQL addons to the same app if that split is ever needed later ([Limitations](https://doc.scalingo.com/databases/postgresql/about/limitations), [Provisioning](https://doc.scalingo.com/databases/postgresql/getting-started/provisioning)), so the option stays open without having to exercise it now. When/if that day comes, stick with a second **PostgreSQL** addon rather than MySQL/MongoDB/Redis/Elasticsearch/OpenSearch/InfluxDB — the app already runs entirely on Postgres (including JSONB columns already in use for `heart_emojis`, theme `colors`), chat data is naturally relational, and same-adapter multi-database setups are the smoothest path in Rails.
2. **No dedicated Scalingo process type for the websocket server.** An earlier draft of this plan called for a new `cable:` Procfile line, scaled and sized independently of the web containers. **Verified against Scalingo's own routing docs before Phase 0 execution and reverted**: Scalingo's router only ever forwards external HTTP/websocket traffic to a process type literally named `web` (or `tcp`, via a dedicated TCP addon for raw non-HTTP protocols) — a custom `cable:` line cannot receive inbound browser connections at all on a single Scalingo app, so it could only do internal/background work, which defeats the point. ActionCable will instead be mounted on the existing `web` process when Phase 2 adds it. Solid Cable is still the right adapter regardless of this — it's what makes broadcasting correct across multiple `web` containers, independent of which process type answers the socket. If websocket volume ever genuinely threatens `web`'s responsiveness, the real Scalingo-native escalation path is a second Scalingo app deployed from the same repo, not a Procfile process type — a decision to revisit with real usage data, not now.
3. **Rails' Solid Cable and Solid Queue** (ship with Rails 8, zero new infra), **both on the primary database**, not a separate one each. An earlier draft called for "each on their own small dedicated database," reasoning that unlike chat's own models, their tables never need to join against `users`/`profiles`/chat data at the SQL level (job/broadcast payloads just carry plain IDs as arguments), so a split wouldn't reopen the cross-database-join problem. **Revisited at Phase 0 execution time**: a dedicated database each still means two new Postgres addons on Scalingo — real recurring cost, not obviously worth paying before chat has any real usage, and not necessary to keep the option open later (same "seam, not a split" reasoning already applied to `ChatRecord` vs. the primary database applies here too). Both `solid_cable` and `solid_queue` document a first-class "single database configuration" path for exactly this — convert the generated schema file into a normal migration and drop the `connects_to` config the install generator would otherwise add — so Phase 0 uses that path instead: one database, revisit a split later if job/broadcast volume ever justifies it. The app currently uses the `async` cable adapter (`config/cable.yml`), which only works within a single process — fine today because nothing uses ActionCable yet, but it would silently break the moment more than one container ran. Solid Cable uses Postgres `LISTEN/NOTIFY`-style polling instead, which works correctly across multiple containers with no Redis addon required (worth knowing: this has higher per-broadcast latency than Redis pub/sub — fine at chat-app scale, and Redis is the natural upgrade later if realtime ever needs to feel snappier under real load). Solid Queue covers the same gap for background jobs — the app currently has no durable job backend (`queue_adapter = :async`, in-process, lost on restart), and chat will eventually want jobs (notification cleanup, etc.). Its supervisor runs embedded inside the same `web` Puma process via `config/puma.rb`'s `plugin :solid_queue if ENV["SOLID_QUEUE_IN_PUMA"]` (the Rails 8 "solo" pattern), avoiding a second container for it too — set with one Scalingo env var (`SOLID_QUEUE_IN_PUMA=true`), no new process type.

### Why not a separate app

The case for splitting is real but weaker than it looks once what's already built is inventoried:

- **Auth would need to be duplicated or bridged.** Sessions are a plain DB-backed model plus a signed cookie (`app/controllers/concerns/authentication.rb`) — there's no OAuth/token layer to hand to a second app. A separate app means either building a session-bridging/SSO flow, or sharing the same Postgres `users`/`sessions` tables across two Rails apps (which mostly just re-invents a monolith with extra deploy steps).
- **Hearts, spoilers, and theming are Ruby methods and ActiveRecord models, not services.** `formatted_inline`/`formatted_description` (`app/helpers/application_helper.rb`) are pure string functions with one small dependency on `Profile.resolve_heart_emoji`/`Profile.heart_emoji_display_name` (class-level lookups against `Profile::HEART_EMOJIS`) — calling them from message rendering is a non-change if it's the same app, but a duplicated implementation (drift risk) or an API round-trip per render if it's a separate one. Same story for the theme system: `belongs_to :theme` plus `ThemeHelper#active_theme_style` reading a couple of controller ivars — trivially extended in-process, awkward across a network boundary.
- **The header notification icon needs cross-cutting data on every page load.** Since notifications must appear in the main site's header (not just on chat pages), a separate app means an API call from the main layout on essentially every request just to render an unread badge — new latency and a new failure mode on pages that have nothing to do with chat. In-process, it's a query against the chat database.
- **Two apps is real ongoing overhead** for a small/solo-maintained project: two Scalingo apps (minimum 2× baseline container cost), two dependency-upgrade cadences, two places to configure error tracking/logging, two CI pipelines.
- **It's the less reversible choice.** A namespaced module with its own database is already most of the way to extractable — if usage ever genuinely demands a separate service, splitting out a `Chat::` engine with its own already-isolated database is a much smaller job than un-merging two apps' auth systems after the fact. Building the separate app now optimizes for a scale problem that doesn't exist yet.

The two isolation costs a separate app *does* solve outright — "a chat bug can't take down the profile app" and "chat's resource needs scale independently" — are covered well enough by the dedicated `cable` process type and the separate database, without paying the auth/API/ops tax.

## Domain and routing

- Use `chat.pluralprofiles.com` as a subdomain of the same app, routed via a `constraints subdomain: "chat"` block in `config/routes.rb` mapping to a `Chat::` controller namespace. No wildcard DNS/SSL needed — just one subdomain record pointing at the same Scalingo app.
- **Servers are paths, not subdomains** (`chat.pluralprofiles.com/servers/:server_uuid/channels/:channel_slug` — see "Server identity" below for why the server segment is a UUID, not a name) — this matches how Discord/Slack actually route despite looking "branded" per workspace, and avoids wildcard DNS/cert complexity for zero practical benefit at this scale.
- **Cookie domain needs one explicit change.** Session cookies are currently set without an explicit `domain:` (`app/controllers/concerns/authentication.rb:54`), so they default to the exact host and won't be sent on a different subdomain. Setting `domain: :all` on the cookie (a standard Rails option meaning "valid for the parent domain and all its subdomains") is what makes an existing login carry over to `chat.pluralprofiles.com` without a second login. Small change, but easy to forget and would otherwise present as "chat logs me out."
- This domain choice is independent of the monolith-vs-separate-app decision and doesn't lock either way — if a real second app is split out later, `chat.pluralprofiles.com` DNS just points elsewhere instead.
- **Local development: use `lvh.me`, not `localhost`.** `lvh.me` (and any subdomain, e.g. `chat.lvh.me`) is a public DNS entry that resolves to `127.0.0.1` — the standard way to exercise subdomain routing locally with no `/etc/hosts` editing. Two Phase 0 follow-ons: (1) add `config.hosts << ".lvh.me"` to `config/environments/development.rb` — confirmed there's no `config.hosts` override there today, and Rails' dev host-authorization only auto-permits literal `localhost`/private IPs, not domains that merely resolve to loopback, so `chat.lvh.me:3000` would otherwise hit a "Blocked host" error; (2) local dev should move from `localhost:3000` to `lvh.me:3000` for the main site too, not just chat — `domain: :all` cookies scope to the parent domain dynamically, so session sharing "just works" locally for `.lvh.me` the same way it will for `.pluralprofiles.com` in production, but only if both the main site and chat are accessed under the same parent domain. Mixing `localhost:3000` and `chat.lvh.me:3000` won't share a session regardless of environment, since they aren't the same domain.

## Server identity — avatar, and an address that doesn't leak or force uniqueness

Two gaps found by sketching the actual UI: servers need an avatar to show in the server rail, and `/servers/understory`-style URLs quietly imply server names have to be globally unique — which also means two different users' servers could collide, or one could learn a same-named server already exists elsewhere. Neither is wanted.

- **Avatar: direct reuse, no new code.** `Group` and `Profile` both already `include HasAvatar` (`app/models/concerns/has_avatar.rb` — `has_one_attached :avatar` plus content-type/size validation). `Chat::Server` includes the same concern. Falls back to the same avatar placeholder convention already used elsewhere (`.avatar--placeholder`, rendering the plural-pride logo) when a server has no avatar set.
- **Servers are addressed by UUID, not name — reusing the exact pattern `Group`/`Profile` already use.** `PluralProfilesUuid.generate` (`lib/plural_profiles_uuid.rb`) plus a `before_create :generate_uuid` and a `to_param` override that returns the UUID instead of the numeric id — copied onto `Chat::Server` unchanged. This means: **no uniqueness constraint on server name at all**, ever — two different users (or the same user) can both have a server called "Understory" with no collision, no error, and no way for either to detect the other's server exists. URLs become `chat.pluralprofiles.com/servers/:uuid`, opaque and private, exactly like group/profile share links today.
- **Channel names stay human-readable, scoped to their server.** Uniqueness is validated per-server (`validates :name, uniqueness: { scope: :server_id }`), not globally — since a channel is only ever addressed *within* an already-disambiguating server UUID (`/servers/:server_uuid/channels/:channel_slug`), there's no collision risk in using the readable name directly in the URL, and no need for channels to carry their own UUID.

## Settings, subtitles, and the channel theme override

Found by sketching the flow further: nothing in the plan so far covers how an owner actually *edits* a server or channel after creating it, channels were missing the `subtitle` field servers/groups/profiles already carry, and the theme override chain for channels was named but never actually specified.

- **Both `Chat::Server` and `Chat::Channel` need a settings/edit screen — normal CRUD, not a new pattern.** `edit`/`update` actions matching the existing `Group`/`Profile` edit forms, gated to the server's owner (ties into the `owner_id`/`role: "owner"` decision already flagged for Phase 1 — whichever way that's resolved, settings-editing is exactly the kind of action that needs an owner check). Server settings: name, subtitle, avatar, theme. Channel settings: name, subtitle, theme override. This belongs in Phase 1 alongside the rest of the CRUD, not a later phase — it's not a new feature, just the other half of "create."
- **`Chat::Channel` gets a `subtitle` field**, same as `Group`/`Profile` already have — rendered with `formatted_inline`, no new formatting work.
- **Theme override chain: channel, then server, then whatever the surrounding context would otherwise resolve to.** A channel with its own `theme_id` set wins; if unset, falls back to the server's `theme_id`; if that's also unset, falls through to the existing site-default/user-override logic already in `ThemeHelper#active_theme_style`. Concretely, that means the helper's `public_theme = @group_theme || @profile_theme` line grows one more link — `@channel_theme || @server_theme || @group_theme || @profile_theme` — rather than chat needing its own separate resolution logic. Settings UI should make the fallback visible (e.g. a channel's theme dropdown defaults to an explicit "Inherit from server" option rather than silently duplicating the server's current theme), so it's obvious when a channel is following the server versus deliberately overriding it.

## Server invites vs. account invites — two separate gates, not one

Initial instinct was to reuse `InviteCode` for server invites too. On investigation this is the wrong call: `InviteCode` is the site's account-creation gate — `RegistrationsController#create` hard-requires a valid, unused `InviteCode` for *every* new account, unconditionally, with no relation to servers or "friendship" at all (that concept doesn't exist in the app yet). Conflating "invite to create a plural-profiles account" with "invite to join this specific server" would tangle two policies that need to evolve independently.

**Two models, one shared pattern:**

- **`InviteCode`** (existing, untouched) — still the only way to create a plural-profiles account. Nothing about it changes.
- **`Chat::ServerInvite`** (new, Phase 4) — belongs to a `Chat::Server`; redeeming it creates a `Chat::Membership` for whoever redeems it and never touches account creation. Copies `InviteCode`'s *pattern* (short generated code, atomic single-use redemption via `with_lock`) as a template, not a shared table or model.
- **Link, not a typed-in code.** The "code" only ever appears embedded in a URL (`chat.pluralprofiles.com/invite/:code`) that gets shared and clicked — nobody manually types anything, matching how Discord/Slack invites actually work in practice despite the "code" name.
- **Single-use by default, same as `InviteCode` — no expiry/usage-count system needed to start.** The most likely flow is one person inviting one specific other person, not posting a standing public link for a community. `InviteCode`'s existing shape (generate a code, first redemption kills it) already *is* "one-time link, click it, you're in," so `Chat::ServerInvite` doesn't need `expires_at`/`max_uses` in Phase 4 at all — that's a purely additive enhancement to bolt on later (reusable/expiring links) if servers ever want public-style invites, not a v1 requirement.

**How the two flows compose** for "someone who already has an account" vs. "someone who doesn't," given the site's registration gate:

- **Existing user**, logged in, clicks a server invite link → straight to `Chat::ServerInvite#redeem!` → `Chat::Membership` created → done. `InviteCode` never enters the picture.
- **No account yet**, clicks the same link while logged out → stash the server invite code in session under its own key (same *pattern* as the existing `return_to_after_authenticating` stash in `app/controllers/concerns/authentication.rb`, but not the same key — the two shouldn't collide) → send them through normal registration, which still requires a separate, valid `InviteCode` from any existing user → once the account exists (and is verified), auto-redeem the stashed `Chat::ServerInvite`.

**Decision**: a `Chat::ServerInvite` will **never** bypass the site-wide registration gate — it only ever grants server membership, never account creation. A brand-new person needs both a site `InviteCode` (from anyone) and the `Chat::ServerInvite` (from the server) to end up a member. This was a deliberate choice to keep the site's invite-only growth policy intact and single-purpose rather than letting server owners indirectly mint site access. It does mean real friction for a first-time invitee (two codes, potentially from two different people) — worth surfacing to server creators in the UI copy when Phase 4 is built, so they know to hand over a spare site invite code alongside the server one if the person they're inviting doesn't have an account yet.

## Default identity — every message needs a resolved profile, not just proxied ones

The app's entire premise is expressing as different profiles, not as the underlying account — and the account/username genuinely can't fill that role: `User` is meant to stay private, and `username` is optional, unused today, and not designed to be a public-facing identity. Without a default, every message in chat would need an explicit short-code just to have a displayed identity at all, which doesn't fit how the rest of the app treats profiles as the primary public-facing concept.

**Design**: each `Chat::Membership` (a user's membership in one server) carries a `default_profile_id` — one of that user's own profiles, chosen by the user, visible and changeable at any time via a persistent "posting as: [avatar] [name] ▾" selector in the chat UI. It's scoped to the server (applies across all of that server's channels); a per-channel override is a natural, easy extension of the same mechanism later if it turns out to be wanted, but isn't needed for v1.

**This is the same mechanism as short-code proxying, not a second one.** The requirement that changing your default must never alter past messages is exactly the invariant already decided for short-code proxying (resolve once, at send time, freeze it on the message — never re-resolve on render). So rather than treating "default profile" and "proxied profile" as two features, `Chat::Message` gets one required `profile_id`, resolved once per message at creation time: use the short-code's target if the message body invokes one, otherwise fall back to the membership's `default_profile_id`. Changing your default going forward only changes what *future* messages resolve to; every message already sent keeps the `profile_id` it was created with, permanently.

**What this changes about the phasing**: identity resolution (default profile → frozen `profile_id` on the message) is basic enough that it belongs in **Phase 1**, not Phase 3 — a message needs *some* displayed profile from the very first working version, well before short-codes or realtime exist. Phase 3 then shrinks to just adding the short-code parser as an override on top of infrastructure that already exists, rather than introducing message-identity resolution as a new concept at that point. Phase build order updated below.

**Pronouns render next to the name and avatar, live — same as avatar, not snapshotted.** While `profile_id` still resolves to a real `Profile`, the message header shows avatar, name, and `Profile#pronouns` all read live from that record, consistent with the rest of the app showing current state rather than a frozen-in-time view. Only the name gets a write-once snapshot (`profile_name`, decided above) for the deleted-profile fallback — pronouns and avatar don't get one, so once a profile is deleted, its old messages fall back to name-only (no pronouns, generic avatar), matching the earlier "name snapshot is enough" call.

**Edge case: a member with no default set yet, and an account with zero profiles at all.** Given the app's whole purpose is profiles, an account with none is an edge case, but chat shouldn't allow a message to exist with no resolvable identity — the natural place to close this is requiring a default profile pick as part of joining a server (part of `Chat::ServerInvite#redeem!` creating the `Chat::Membership`), with a nudge to create a profile first if the account doesn't have one yet, mirroring how the app already gates account creation on an invite code rather than allowing an incomplete state.

**Edge case: the referenced profile gets deleted later.** Resolved, not just flagged — soft-deleting `Profile` was considered and rejected: there's no soft-delete anywhere in this app today (`Profile#destroy`, `app/controllers/our/profiles_controller.rb:58`, is a real hard delete), and retrofitting one onto the core `Profile` model just to serve chat's history-rendering needs would be a disproportionate, invasive change to deletion behavior across the *entire* app — plus it works against the point of deleting a profile at all, if someone deletes one specifically to stop being associated with it. Instead, reuse the pattern already established for exactly this situation: `Profile` already has `has_many :copies, ..., dependent: :nullify` (same on `Group`) for references that should survive a deletion by going blank rather than cascading or dangling. Same treatment here:

- `Chat::Message.profile_id` — required when a message is *created* (can't post as nobody), nullable afterward via `dependent: :nullify` from `Profile`. Rendering checks: profile present → normal avatar/name/pronouns/link; profile nil → generic "Deleted profile" placeholder, no link. Message body and timestamp are untouched either way.
- `Chat::Membership.default_profile_id` gets the same `dependent: :nullify` — a deleted default just goes back to unset, funneling into the same "must pick a resolvable default before posting" gate from the case above, plus the existing "must belong to the same user" validation pattern from `GroupProfile`/`GroupGroup`.

This only works cleanly as a normal FK-backed Rails callback *because* chat models stay in the primary database (see the database decision above) — it wouldn't behave the same way across a cross-database split.

**Decision: also snapshot the profile's name onto the message, nothing more.** `Chat::Message` gets a `profile_name` string column, captured once from the resolved profile at creation time, write-once, never updated afterward. It is **not** used for normal rendering — while the profile still exists, display always does the live lookup via `profile_id` (current name/avatar/pronouns, consistent with how the rest of the app shows current state rather than historical snapshots). It only comes into play as the fallback once `profile_id` has been nulled out by a deletion: instead of a fully generic "Deleted profile," the placeholder can read "Alice (deleted)" using the frozen name — still no avatar (falls back to a generic placeholder image) and no pronouns, deliberately kept to just the name. A small addition at Phase 1 schema time that pays for itself specifically when deletion happens later, rather than something to retrofit after the fact.

## Phased build order

**Phase 0 — infrastructure groundwork.** Add the `ChatRecord` base class (pointed at the primary database for now — see the revised database decision above); add `solid_cable` and `solid_queue` gems and run their install generators (`bin/rails generate solid_cable:install`, `bin/rails generate solid_queue:install` — each sets up its own migrations/config, not just a Gemfile line), then collapse both onto the primary database via each gem's documented single-database path (see the revised database decision above) rather than provisioning new Postgres addons, with Solid Cable as the production ActionCable adapter; **no `cable` process type** — ActionCable mounts on the existing `web` process (see the revised routing decision above), and Solid Queue's supervisor runs embedded in `web` via `SOLID_QUEUE_IN_PUMA=true`; add the `chat.` subdomain route constraint and the `domain: :all` cookie change; add the `config.hosts` allowance for local subdomain testing (done — see "Domain and routing" above). No user-visible feature yet — this phase is what makes the rest of the plan actually hold up under the memory/growth constraints, so it comes first rather than being retrofitted later.

**Phase 1 — core data model, no realtime yet.** `Chat::Server` (includes `HasAvatar`, plus `uuid`/`to_param` via the `PluralProfilesUuid` pattern — see "Server identity" above, no name-uniqueness constraint), `Chat::Membership` (first multi-user join model, includes `default_profile_id`), `Chat::Channel` (name unique per-server, not globally; includes `subtitle`, same field `Group`/`Profile` already have), `Chat::Message` (includes `profile_id` — required at creation, nullable afterward via `dependent: :nullify` if the profile is later deleted — resolved from the membership's default and frozen at creation, plus a write-once `profile_name` snapshot for the deleted-profile fallback, see "Default identity" above), all on the primary database via `ChatRecord`, with ordinary FKs/joins to `User`/`Profile`. Plain HTTP CRUD (page reloads, no websockets yet) so the data model gets validated before realtime complexity is layered on. Message rendering uses `formatted_description`/`formatted_inline` unchanged. Theme ivar chain extended per "Settings, subtitles, and the channel theme override" above. Owner-gated settings/edit screens for both `Chat::Server` and `Chat::Channel`, same shape as existing `Group`/`Profile` edit forms. Message creation gets a `rate_limit`, reusing the same Rails 8 pattern already in use on login/password (`app/controllers/sessions_controller.rb`, `app/controllers/passwords_controller.rb`) — set generously high, purely to blunt accidental flooding/runaway scripts rather than to constrain normal use, from the very first version rather than bolted on once it's already a problem. Two further open decisions to make here: whether a server's creator is captured via a plain `owner_id` on `Chat::Server`, purely via a `role: "owner"` row in `Chat::Membership`, or both; and how joining gates on picking a default profile before a first message can be sent — normal schema/UX-design calls for this phase, not resolved by this document.

**Phase 2 — realtime.** ActionCable channel per `Chat::Channel` broadcasting new messages via Turbo Streams over Solid Cable; a per-user notification stream powering the header icon/dropdown on the main site (unread counts, links to the relevant server/channel).

**Phase 3 — profile proxying.** Short-code-triggered per-message identity override (Tupperbox-style) on top of the identity-resolution infrastructure already built in Phase 1: a unique-per-user short code on `Profile`, and a small parser for the message-send path that resolves to that profile's `id` instead of the membership default for that one message — doesn't touch the stored default, matching Tupperbox's "proxy this message" (not "become this profile going forward") behavior.

**Phase 4 — membership, invites, moderation.** `Chat::ServerInvite` (own model, `InviteCode` pattern copied — see "Server invites vs. account invites" above), membership roles, and a blocking model — this is the phase that needs the most original design work since nothing in the codebase does user-to-user blocking today.

**Phase 5 — threads.** Simple self-referential threading vs. a dedicated thread model is a real design choice best made once real usage patterns from Phases 1-2 exist, not now.

**Deliberately out of scope for this roadmap:** message editing and deletion. Wanted eventually, but cleanly separable — they slot in as their own later feature once the core send/display/proxy/membership pieces above exist, rather than needing to be designed alongside them now.
